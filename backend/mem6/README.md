# M6 — Explainable AI Security Advisor

Implements the **M6** module of the PS4 Interface Contract v1.0: consumes
M5's `RiskAssessedFinding`, produces M7's `ExplainedFinding`. Built with
Python + FastAPI. **M6 never computes, modifies, or overrides `risk_score`
or `risk_level`.**

---

## 1. What M6 does

M5 calculates *how risky* a finding is. M6 explains *why*, for two
audiences:

- **Security Analyst View** (`explanation.technical`) — evidence, attack
  context, what to check.
- **Management View** (`explanation.management`) — business impact,
  urgency, what to prioritize.

It also identifies the `top_risk_drivers` behind M5's score and provides
a `remediation.recommended_action` — all strictly grounded in the
evidence M5 supplied. It does **not** own SLA timers, ticketing, or
workflow status — that's M7.

---

## 2. Architecture

```
M5 JSON (RiskAssessedFinding)
        |
   FastAPI route (/api/v1/explain)
        |
   Pydantic validation (input_models.py)
        |
   explanation_service.generate_explained_finding()
        |
        |-- risk_score / risk_level: DIRECT COPY from input (never computed)
        |-- top_risk_drivers: deterministic mapping from score_breakdown
        |-- priority: deterministic mapping from risk_level
        |
        |-- Try: llm_service (Anthropic, if API key set)
        |         -> structured JSON response, validated
        |-- Fallback: fallback_service (rule-based, always succeeds)
        |
   ExplainedFinding (Pydantic-validated)
        |
   -> M7
```

The risk-score guardrail lives in exactly one function
(`_passthrough_score` in `app/services/explanation_service.py`) and is
asserted against before the response is ever returned.

## 12. LLM mode

If `ANTHROPIC_API_KEY` is set in `.env`, `/api/v1/explain` calls Claude
with a strict grounding system prompt (`app/prompts/explanation_prompt.py`)
that:
- Only receives the evidence fields M5 actually supplied (missing fields
  are omitted, not sent as null, so the model isn't invited to guess).
- Is instructed to say information is unavailable rather than assume it.
- Is instructed to never state or imply a different risk score.
- Must return `{technical, management, recommended_action}` as JSON —
  `top_risk_drivers` and `priority` are computed deterministically in code,
  never by the LLM.

## 13. Fallback mode

If the LLM call fails for any reason — no key, timeout, malformed JSON,
failed validation — `app/services/fallback_service.py` builds the same
three fields deterministically from the evidence fields directly. This
path has zero external dependencies and always succeeds, so the demo
never breaks on wifi or API issues. `metadata` isn't part of the frozen
output contract, but you can see which path ran via server logs
(`Generated ExplainedFinding for ... via <llm|template_fallback> path.`).

## 14. How M6 integrates with M5

M5 sends a `RiskAssessedFinding` to `POST /api/v1/explain`. M6 treats
`risk_assessment.risk_score` and `.risk_level` as read-only and echoes
them unchanged. All other threat intel / asset / scanner fields are
optional except `finding_id`, `asset_context.asset_id`, and
`risk_assessment` itself.

## 15. How M6 integrates with M7

M7 should read:
- `risk_score` / `risk_level` — as **input** to M7's own SLA matrix. M7
  defines that mapping, not M6.
- `remediation.recommended_action` and `.references` — as ticket
  description content.
- `explanation.technical` / `.management` — for human-readable ticket
  context or notifications.

M7 owns SLA timers, ticket creation, assignment, escalation, and workflow
status. M6 never outputs any of those.
